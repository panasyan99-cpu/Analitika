# Важно для 2.4.3

В обычной работе ручной ввод реквизитов больше не требуется: сайт использует приватную серверную конфигурацию и запускает проверку автоматически при открытии склада. Инструкция ниже остаётся аварийным сценарием для администратора.

# Миграция склада 2.4.0: таблица «Позиции поставок»

Версия 2.4.0 больше не разрешает рабочие операции по старой схеме. До создания
таблицы «Позиции поставок» приёмка, новая поставка и передача в бухгалтерию
блокируются, поэтому один SKU не сможет перезаписать данные другой поставки.

## Автоматический способ на сайте

1. Откройте **Сувениры и касты на складе → История → Обслуживание**.
2. Раскройте **«Создать / проверить таблицу “Позиции поставок”»**.
3. Введите email и пароль Baserow пользователя с правами Builder/Admin.
4. Подтвердите действие и нажмите **«Создать и мигрировать»**.
5. Скачайте JSON-отчёт и проверьте позиции со статусом **«Требует проверки»**.

Пароль не сохраняется. Он используется только для получения короткого JWT,
поскольку обычный Database Token может менять строки, но не структуру таблиц.

## Альтернативный запуск из Windows

```text
RUN_SUPPLY_LINES_MIGRATION.bat
```

Скрипт создаёт таблицу и служебные поля, переносит старые данные и выводит
фактический ID новой таблицы.

## Создаваемые поля

| Поле | Назначение |
|---|---|
| Строка поставки | `SUP-... — SKU` |
| Поставка | связь с реестром поставок |
| Товар сувенирки | связь с товаром |
| Комплектующее | связь с комплектующим |
| По документу, шт. | количество в конкретной поставке |
| Принято, шт. | принято из конкретной поставки |
| Передано в бухгалтерию, шт. | уже передано из этой поставки |
| Номера коробок | коробки конкретной строки |
| Статус | состояние строки поставки |
| Комментарий | служебная информация |
| Версия | версия записи |
| Активна | активность строки |
| Command ID | защита от повторного проведения |
| Создано из импорта | источник миграции/импорта |

Дополнительно создаются служебные поля в таблицах «Операции» и «Поставки»:
ссылка на позицию поставки, ссылка на исходную операцию, Command ID, причина
корректировки, статус документа, Import ID и статус импорта.

## Миграция старых данных

- повторный запуск не создаёт дубли;
- принятые и переданные количества восстанавливаются по операциям, где это
  возможно;
- SKU, которые в старой схеме были связаны сразу с несколькими поставками,
  получают статус **«Требует проверки»**;
- выдуманные количества для комплектующих не создаются;
- сайт автоматически обнаруживает таблицу по имени после миграции.

После миграции рекомендуется записать фактический ID в Streamlit Secrets:

```toml
[baserow]
supply_lines_table_id = 646  # пример; используйте фактический ID из отчёта
```
